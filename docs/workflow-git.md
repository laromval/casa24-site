# Git/GitHub процесс и деплой на хостинг

## Зачем это нужно

Команда работает с разных компьютеров. Без единого процесса это быстро превращается в «кто последний зашёл по FTP, тот и прав». GitHub — источник истины по коду и решениям, хостинг casa24.md — куда попадают только проверенные изменения.

## Ветки

- `main` — соответствует тому, что реально опубликовано на casa24.md. Никаких прямых коммитов в `main`.
- `dev` — интеграционная ветка, куда сливаются готовые задачи перед релизом.
- `feature/<короткое-имя>` или `fix/<короткое-имя>` — одна ветка на одну задачу из `docs/priorities.md`. Пример: `fix/p0-price-model-r14`, `feature/p1-alt-tags`.

## Процесс на одну задачу

1. Взять задачу из `docs/priorities.md`, поставить статус `in-progress`.
2. Создать ветку от `dev`: `git checkout -b fix/p0-price-model-r14 dev`.
3. Внести изменения (код — в репозитории; правки в самом WordPress — документировать в описании PR: что именно менялось в wp-admin/WooCommerce, если это не файлы кода).
4. Открыть Pull Request в `dev` с описанием: что сделано, какой пункт `docs/priorities.md` закрывает, как проверить.
5. qa-agent прогоняет чек-лист (`.claude/agents/qa-agent.md`) — либо на staging, либо на превью, в зависимости от типа изменения.
6. После аппрува — merge в `dev`. Статус задачи → `review`, затем `done` после подтверждения на хостинге.

## Релиз на хостинг

1. Когда в `dev` накопился согласованный набор готовых задач — координатор принимает решение о релизе.
2. `dev` мержится в `main` через Pull Request (не напрямую).
3. dev-agent применяет изменения на боевой хостинг casa24.md — вручную через wp-admin/WooCommerce там, где изменение контентное, или через SFTP/WP-CLI, где изменение в коде/теме/плагинах. Доступы — из менеджера паролей (см. `docs/security-notes.md`), не хранить их в этом репозитории и не передавать в открытых чатах.
4. После деплоя — быстрая проверка на живом сайте (smoke test): главная открывается, корзина работает, цены на месте, RU/RO переключение работает.
5. Если что-то пошло не так — откат на хостинге до прежнего состояния (важно иметь бэкап перед каждым релизом) и разбор причины перед повторной попыткой.

## Что коммитить, а что нет

**Коммитить:** документацию проекта (этот репозиторий), кастомный код темы/плагинов (если есть), конфигурационные файлы без секретов, CSV-экспорты каталога для истории изменений (без персональных данных клиентов).

**Не коммитить:** пароли, ключи API, `wp-config.php`, полные бэкапы БД (`.sql`), медиатеку `wp-content/uploads` целиком (слишком тяжёлая для git — для этого нужен обычный бэкап на хостинге). `.gitignore` в репозитории уже настроен на эти паттерны.

## Экстренные исправления (hotfix)

Если на живом сайте критическая проблема (например, сайт не открывается или оплата не проходит) — можно исправить напрямую на хостинге без ожидания полного процесса, но:
1. Сразу после исправления — зафиксировать то же изменение в репозитории отдельным коммитом/PR, чтобы `main` не разошёлся с реальным состоянием сайта.
2. Сообщить координатору, что был hotfix в обход процесса, и почему.
